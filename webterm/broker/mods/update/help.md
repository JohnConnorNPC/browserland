The update chip tells you whether the build you are looking at is current with upstream, without opening a shell to run `git fetch`. Turn it on or off from Control Panel → Mods.

The mod ships **disabled by default**, and enabling it is not on its own enough to make the broker talk to GitHub. The broker has its own switch — `update_check_enabled` in its config, also off by default — and until an operator sets it the check answers "update checking is switched off on this broker" and no outbound request is made. That split is deliberate: the mod's toggle governs what your browser draws, the broker's governs whether the machine reaches the internet. When it is on, the broker makes the request once and caches it for a day, so every tab and every browser shares one call rather than each burning GitHub's rate limit.

The chip has four states. **Up to date** means your commit matches upstream. **N behind** means upstream has commits you do not. **Ahead** means this checkout has commits upstream has never seen — a development checkout, not a stale one. **Version ?** means the check could not be established, and it is the state the mod falls back to for every failure: offline, rate-limited, no git checkout, or an answer GitHub could not give. A version checker that said "up to date" when it meant "I could not check" would be worse than none, because you would trust it. By default the chip hides itself while the build is current, so it only takes up taskbar space when there is something to say; an unknown never hides.

Click the chip to open the **Update check** window. It shows your build and commit, the upstream build, how far apart they are, when the check last ran, and a link to the comparison or release page on GitHub. When the state is unknown it says why in plain words. When you are behind it spells out the manual update: stop the broker, `git pull --ff-only`, reinstall dependencies if `pyproject.toml` changed, then start it again and reload the page.

Two things the window deliberately does not claim. It does not inspect your working tree — build ids carry no dirty-tree marker, so uncommitted local changes are invisible and the report reflects your last commit only. And it never reads "ahead" from GitHub simply failing to compare: that comparison also fails for a commit that was garbage-collected, a repository that moved, or a branch that was force-pushed, so an unanswerable comparison is reported as unknown rather than guessed at.
